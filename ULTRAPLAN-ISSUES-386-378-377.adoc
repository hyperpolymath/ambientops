== Root Cause Analysis

=== Issue #386 — gitleaks failure

**Evidence chain**:

1. `secret-scanner.yml` pins `@74d2f66f` — calls the estate reusable
2. The reusable installs gitleaks 8.18.4 (checksum-verified), fetches the estate baseline, stages it as `.gitleaks-estate.toml`
3. No `.gitleaks.toml` exists in this repo → scanner uses `.gitleaks-estate.toml` directly
4. The estate baseline allowlists: lockfiles, vendored yarn, `.gitleaks-estate.toml` itself, published test vectors (RFC 8032), hex fingerprints, CamelCase type names, doc filenames, ellipsis-terminated placeholders, repeated-character masks, monotonic hex walks, snake_case test fixtures
5. **What is NOT allowlisted**: the A2ML/TOML metadata in `.machine_readable/`, STATE.a2ml, ECOSYSTEM.a2ml, META.a2ml, AGENTIC.a2ml, PLAYBOOK.a2ml, NEUROSYM.a2ml — these contain key-value pairs with high-entropy values (SHA hashes, UUIDs, hex strings, version identifiers) that trip `generic-api-key`
6. The scan step runs `gitleaks detect --source . --no-git --redact --no-banner --verbose --config <CONFIG> --exit-code 1`
7. The git-history pass also runs, catching any committed-then-deleted secrets

**Root cause**: Repo-specific false positives in machine-readable metadata files. The repo needs a `.gitleaks.toml` that extends the estate baseline and adds path-based or value-based allowlist entries for its A2ML files.

=== Wave 1: Unblock main — gitleaks (Issue #386)

**Priority**: P0 (security gate, blocks every PR)

==== Step 1.1: Create repo-local `.gitleaks.toml`

Create `.gitleaks.toml` at the repository root with the following design:

1. **Inherit the estate baseline** via `[extend] path = ".gitleaks-estate.toml"` — this is the pattern the reusable expects
2. **Allowlist the A2ML/metadata directory** by path for `generic-api-key` false positives — the `.machine_readable/` directory contains TOML and A2ML files with high-entropy keys that are NOT credentials (SHA commit refs, version strings, hex-encoded metadata)
3. **Add value-based regexes** for repo-specific false positive patterns (e.g., hex commit SHAs in STATE files, A2ML key names with CamelCase)

```toml
# SPDX-License-Identifier: MPL-2.0
# .gitleaks.toml — ambientops repo-local gitleaks config.
# Extends the estate baseline staged by the reusable workflow.

[extend]
path = ".gitleaks-estate.toml"

[allowlist]
description = "ambientops: machine-readable metadata false positives"
paths = [
  # A2ML/TOML metadata files contain high-entropy identifiers
  # (commit SHAs, version strings, hex-encoded keys) that are NOT credentials.
  '''(^|/)\.machine_readable/''',
  # Session state files
  '''(^|/)\.session/''',
  # Hypatia baseline metadata
  '''(^|/)\.hypatia/''',
]
```

**Rationale for path-based allowlist**: The `.machine_readable/` directory is a controlled, generated metadata store. All files in it are machine-generated state checkpoints (STATE.a2ml, META.a2ml, ECOSYSTEM.a2ml, etc.) that contain no real credentials. This is narrow enough to not blind the scanner elsewhere.

**Validation**: After creating, verify with `gitleaks detect --source . --no-git --config .gitleaks.toml --verbose --exit-code 1` (if gitleaks is available).

==== Step 1.2: Run gitleaks git-history pass

The git-history pass scans all committed content. If historical commits contain real secrets (not just metadata), those need to be either:
- **Rotated** (if real) — the secret is already exposed in git history
- **Allowlisted by value** (if false positive) — add a `regexes` entry

This step requires running the actual gitleaks binary against the full history. Since we don't have gitleaks in this sandbox, the fix should be pushed and the CI run observed.

==== Deliverable
