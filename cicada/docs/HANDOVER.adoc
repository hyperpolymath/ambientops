== Project Overview

CIcaDA (Palimpsest Crypto Identity) is a comprehensive cryptographic identity management tool designed to generate quantum-resistant SSH keys with advanced security features for ethical technology development.

[cols="1,3"]
|===
| *Full Name* | Palimpsest Crypto Identity (CIcaDA)
| *UUID* | `449d71e4-0569-4032-8a3c-f519b3386ebb`
| *Language* | Julia 1.9+
| *License* | PMPL-1.0-or-later (Palimpsest License)
| *Parent Repo* | `ambientops` (hybrid monorepo, `cicada/` subdirectory)
| *Total Implementation* | ~3,500+ lines of Julia code + tests + documentation
| *Motto* | "Securing Digital Identities with Quantum-Resistant Precision"
|===

== Core Features

* *Quantum-resistant key generation* -- Classical (Ed25519, RSA, ECDSA) and post-quantum (Dilithium, Kyber) with hybrid mode
* *Multi-factor authentication* -- TOTP-based MFA (planned Phase 2)
* *Secure key storage* -- 0600/0700 permissions, JSON metadata, UUID tracking
* *GitHub integration* -- Upload, list, delete SSH keys via GitHub API
* *Cross-platform support* -- Linux, macOS, Windows (CI tested)
* *Automated key rotation* -- Schedule-based, auto-expiry, and emergency rotation
* *Security auditing* -- Comprehensive key analysis, strength assessment, and audit trail
* *Backup and recovery* -- Individual/bulk backups with retention management

== Technical Architecture

=== Primary Language

*Julia 1.9+* -- chosen for strong numerical computing, native C interop for cryptographic libraries, multiple dispatch for clean API design, and cross-platform support.

=== Cryptographic Foundations

[cols="1,2,2"]
|===
| *Component* | *Technology* | *Purpose*

| Key Generation (Classical)
| Ed25519, RSA-2048/4096, ECDSA-P256/P384
| SSH key pair generation using OpenSSH_jll bindings

| Key Generation (PQC)
| Dilithium2/3/5, Kyber512/768/1024
| Post-quantum signatures and key encapsulation (NIST FIPS 204/203). Currently stub implementation.

| Hybrid Mode
| Ed25519 + Dilithium3
| Defense-in-depth: if either algorithm is broken, the other provides fallback

| Key Derivation (Planned)
| Argon2id
| Passphrase-based key derivation for backup encryption, resistant to GPU/ASIC attacks

| Encryption at Rest (Planned)
| AES-256-GCM
| Authenticated encryption for private key backups

| Hashing
| Nettle.jl (SHA-256+)
| Fingerprint computation and integrity verification
|===

=== Authentication

* *TOTP-based multi-factor authentication* -- Planned for Phase 2, will use TOTP.jl for enrollment and verification
* *Hardware security keys* -- Planned for Phase 2 (YubiKey support)
* *Secure key storage* -- OS-level permissions (0600/0700), JSON metadata with UUIDs

== Key Technical Components

=== 1. Secure Key Generation Module

Generates Ed25519/RSA/ECDSA key pairs using OpenSSH_jll (cryptographically secure RNG). PQC stubs establish the architecture for Dilithium/Kyber integration via NistyPQC.jl. Hybrid mode combines classical + PQC for maximum security.

*Source*: `src/keygen/classical.jl`, `src/keygen/postquantum.jl`, `src/keygen/types.jl`

=== 2. Multi-Factor Authentication System

Planned Phase 2 feature. Will implement TOTP authentication using TOTP.jl with user enrollment and verification workflows. Hardware security key support (YubiKey) also planned.

=== 3. GitHub SSH Key Integration

Automates uploading, listing, and deleting SSH keys on GitHub via the GitHub API. Supports both CLI-provided and configuration-file tokens. Includes token validation.

*Source*: `src/integrations/github.jl`

=== 4. Cross-Platform Installer Generator

Installation script (`install.sh`) handles dependency checking and setup. Platform-specific packaging (Windows/macOS/Linux) planned for Phase 2.

*Source*: `install.sh`

=== 5. Advanced Logging and Audit Mechanisms

Logs all key generation, authentication, and GitHub integration events. Security audit command provides strength assessment, expiration checking, and algorithm analysis for all stored keys.

*Source*: `src/utils/logging.jl`, `src/validation/verify.jl`

* *Quantum-resistant cryptography* -- All algorithms chosen with post-quantum transition in mind
* *Comprehensive entropy collection* -- OpenSSH_jll uses system CSPRNG
* *Secure key derivation* -- Argon2id for passphrase-based operations (planned)

* *Defense in depth* -- Hybrid keys, restrictive permissions, backup encryption

== Key Technical Challenges

[%header,cols="1,1,3"]
|===
| Challenge | Priority | Notes

| Cross-platform key generation
| *Critical*
| Ensuring consistent and secure key generation across Linux, macOS, Windows. OpenSSH_jll provides cross-platform bindings.

| Secure key storage
| *Critical*
| Protecting private keys from unauthorized access. Currently uses filesystem permissions; Phase 2 adds encryption at rest.

| GitHub API integration
| Medium
| Handling rate limits and authentication securely. Token management via config or CLI.

| PQC implementation maturity
| *Critical*
| NistyPQC.jl must reach production quality before CIcaDA can offer real PQC. Current stubs establish architecture only.

| Cross-platform installers
| Medium
| Need Inno Setup (Windows), pkgbuild (macOS), and distribution packages (Linux).
|===

== Known Issues and Limitations

1. *PQC is stub only* -- Post-quantum algorithms produce simulated key material, not cryptographically secure PQC keys
2. *No MFA yet* -- Single-factor key access; TOTP planned for Phase 2
3. *Backups unencrypted* -- Backup files are readable without passphrase; encryption planned for Phase 2
4. *malware-scanner not integrated* -- Submodule exists but not wired into key operations
5. *Julia startup latency* -- CLI has noticeable startup time due to Julia's JIT compilation
6. *Ed448 not implemented* -- Original handover mentions Ed448; CIcaDA uses Ed25519 (more widely supported, adequate security)
